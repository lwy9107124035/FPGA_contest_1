## 〇、第一轮上板反馈后的追加结论（v12.2，重要）

第一版（v12.1）烧上去后用户反馈：「还是会花屏，**疑似只显示两张图片**，
每次切换出现 **5 条竖长条**，一张是花组成的爱心，另一张上红下蓝 8:2。」

据此又定位到**第二个独立缺陷**：

### 0.1 「只显示两张图片」= `scale_en` 上电默认 0

`msg_ink.v` 原代码：`scale_en <= 1'b0;`（v10.3 注释「缩放默认关」，为"零回归"）。
而 `multi_res=0` 时 `bmp_read` 的 `header_match` **只认「恰 640×480」**
（`(width==640)&&(height==480)`）——**多分辨率图在装载阶段就整组被拒**。
演示卡 8 张里只有 640×480 那张能播 → 「只显示两张」（含直通那张）。

**更糟的次生效应**：每被拒一次 → **0.8s 装载超时 → 静默重试 ×2 → `load_abort` → 全量重扫**
（黑屏 ~1.6s）。按一次 NEXT 就轮一遍 → 屏幕反复黑/闪/残帧，
**看起来就是「花屏」**。这也解释了 09-08 记录里那些 `stall burst` / `LIST 振荡` 告警。

### 0.2 修法：默认 `scale_en = 1'b1`

**为什么必须改默认、不能叫用户敲 `SC 1`**：本机 **CH340/串口器件不在位**
（`GetPortNames()` 列得出 COM4，但 `serial.Serial('COM4')` 报 FileNotFoundError），
**播控台发不出任何命令**，用户只能按板上物理键
→ **凡"必须先发命令才可用"的功能，在这个板子上等于不可用。**

安全性：640×480 仍走**未改动的 pass 直通**；超出合法范围的图仍被 `mr_ok` 拒收；
而缩放链路已在真板速率下**全分辨率验证通过**（见第二节）。

### 0.3 关于「5 条竖长条」

`vout_fx.v` 的**百叶窗转场**（`FD 3`）实现正是 **10 条 64px 竖条**
（`blinds_ok = (t >= slat_thr(px[9:6]))`），逐条揭开、历时约 32 帧（0.53s）——
切图时看到若干条竖条，是**该特效的设计表现**。

但 `msg_ink` 上电默认 `fd_mode = 2'd0`（**硬切**，`xfx_on` 恒 0），
所以**默认不该出现竖条**。若新一轮仍能看到竖条，则它来自别处（读通道或卡内容），
需要用户再描述一次现象（出现时机/持续多久/是否每行同样位置）。

### 0.4 第二轮反馈后的处置（v12.3）：先补「观测口」，不盲改

第二轮反馈：「**还是两张，还在，有竖条，一闪而过**」。
→ `scale_en=1` 并**没有**让图片变多，说明「只显示两张」还有别的原因；
   而竖条是**瞬态**（只在切图瞬间），常驻异常另有其因。

**核心困难：这块板子的串口不可用，我拿不到任何遥测**（`LIST?`/`WHY?` 全废）。
而「只显示两张」有两种**性质完全不同**的可能，不区分就无法决定改什么：

| 可能 | 性质 | 该做什么 |
|---|---|---|
| (a) 卡里本来就只有 2 张 | **不是 bug**（「红上蓝下 8:2」可能只是那张照片本身，比如日落） | 什么都不用改 |
| (b) 扫描只登记了 2~4 张（`SCAN_TARGET_COUNT = 3'd4`），用户无法下发 `SCAN32` 扩扫 | **是限制** | 改扫描深度 |

**处置：v12.3 在顶层把数码管的低两位接成「已登记图片张数」（十六进制 00..3F）**，
让数码管成为遥测通道 —— 下次就能直接读出「到底登记了几张」。

顺手修掉一个 **declare-after-use**：`list_cnt/list_depth` 原声明在 `top` 的 L419，
而数码管在 L232 就要用它 → 会生成 **1bit 隐式网**并与 6bit 声明冲突
（**本文件历史老坑**，与 `osd_x/osd_y/vout_osd` 同族）。已把声明提到 L70 附近。
顶层全依赖 iverilog 编译通过、**零 implicit 告警**。

**故意没动 `SCAN_TARGET_COUNT`**：改成 16 有实测风险（archive 记录「4 图卡 target=7 全卡爬要 37 秒」），
稀疏卡上可能显著拖长开机。**等数码管读数回来再定。**

## 一、一句话结论

**花屏不在环形缓冲，在缩放器的「输出节奏」。**
缩放路原本把一整行 640 像素在 2560 拍内推完（1 字/4 拍），灌向一个只有 **512 深**的 FIFO，
逼得 SDRAM 写侧二选一：**要么溢出丢字（0x18 卡死）**，**要么长时间占住写口把显示读口饿死（=花屏）**。
改为 **1 字/32 拍**后，FIFO 水位从顶格 511 掉到 50，两个病一起消失。

## 二、为什么 09-10 的结论是错的（证据）

09-10 的推理链条是：写侧每拍 1 像素 → 写比读快 → 环形 4 行被覆写。
**问题出在最前面那个前提**：真板 SD 根本没有"每拍 1 像素"这回事。

| 环节 | 实测/推算 | 依据 |
|---|---|---|
| SPI 时钟 | ≈25 MHz | `spi_master.v` 每字节 = 16 半周期 ×(clk_div+2)，`SPI_HIGH_SPEED_DIV=0` |
| 字节速率 | ≈32~36 个 100MHz 周期/字节 | 同上 |
| **像素速率** | **1 像素(3B) ≈ 96~108 拍** | 3 字节/像素 |
| 实测旁证 | **1 像素 ≈ 180 拍** | `sd_card_bmp.v` 注释「正常加载 ~0.55s」÷ 640×480(921KB) |
| 旧 TB 的源 | **1 像素/拍** | `tb_scaler_burst.v` / `tb_v103_fw.v` |

**旧 TB 的源比真板快约 100 倍。** 而环形被覆写需要源快于 **3.2 拍/像素**
（写侧要在读侧绕完 4 槽的 10240 拍内推进 >4 行 = 3200 像素）。
真板物理下限 96 拍/像素，**比这个门槛慢 30 倍** —— 环不可能被覆写。

**仿真实证**（新建 `tools/tests/tb_scaler_real.v`：真速率源 + 独立可解码样图 + 设计意图几何）：

| 源分辨率 | 真速率 | 结果 |
|---|---|---|
| 320×240 | 180 拍/像素 | **wrong px = 0 PASS** |
| 800×600 | 180 拍/像素 | **wrong px = 0 PASS** |
| 1024×768 | 180 拍/像素 | **wrong px = 0 PASS** |
| 640×200 | 180 拍/像素 | **wrong px = 0 PASS** |
| 1280×360 | 180 拍/像素 | **wrong px = 0 PASS** |
| 400×800 | 180 拍/像素 | **wrong px = 0 PASS** |

→ 缩放链路在真板速率下**渲染完全正确**，无需 B3，无需动 SDRAM 仲裁层。

## 三、真根因与修复

### 3.1 为什么 b20 干净、b22q/b23 都花

- **b20 干净**：当时卡上只有 640×480 → `guard_c=c_ex0` 走 **pass 直通**，突发根本不发生。
- **换成多分辨率图组后** 7/8 张进缩放路 → 突发暴露。
- **b23 为什么没修好**：它的 `O_wr_busy` 诚实口径只在「空 FIFO 泊车」时松手，
  **突发期间只要有料就仍 busy** → 显示读照旧被饿死。

### 3.2 改了哪一行

`img_scaler.v` 缩放路出货门控：

```verilog
// 旧 (b-22 真四分频)：一整行 640 字在 2560 拍内推完
if ((row_ok || eovr) && (pass || (half_cnt[1] && half_cnt[0]))) begin

// 新 (v12.1)：1 字/32 拍，瞬时灌入速率降到 1/8
reg [4:0]  rd_tick;
wire       rd_gate = (rd_tick == 5'd31);
if ((row_ok || eovr) && (pass || rd_gate)) begin
```

**为什么 32 拍是安全的**：源侧平均只需 **1 字/~280 拍**
（SD 每像素 ~180 拍 × 800 入/512 出），取 32 拍仍**快 8 倍**，
所以
1. **不拖慢装载**（装载时间由 SD 决定，依旧 ~0.86s，远大于输出的 98ms）；
2. 输出仍比源快 3 倍以上，**环形不会被追越**（即使没有下面的兜底也安全）。

### 3.3 附带加的一道保险：`src_pause`

给 `img_scaler` 加了 `src_pause` 输出（`rows_done >= syc+2` 时置起），
经 `bmp_read.pause` → `sd_card_bmp.pause` → 顶层，在**扇区间隙**暂停「下一个扇区读」。
安全不变式 `rows_done <= syc+3`（环 4 槽，只要「行 syc+4 未被写」，slot syc%4 里就仍是行 syc）。

安全性：`sd_card_sec_read_write` 在 `S_WAIT_READ_WRITE` 天然等待 `sd_sec_read`，
**扇区间拉低只是等待，不打断已发出的 CMD17，无超时/协议风险**。
真速率下它是 no-op（源本来就是瓶颈），只作兜底。

## 五、顺手修掉的两个「校验台自己错」的坑

这次最大的教训是：**校验台比被测设计更容易错**。两处都修了：

1. **`scaler_golden_cmp.py` 几何公式错位**（仅 4:3 时正确）
   - 旧：`t_nd = (w*480)//w`（恒 480）；DUT 实际是 `est_w ? (h*640)/w : (w*480)/h`
   - 后果：800×600 能过，**1280×720 / 400×800 一律误判**
   - 修正后与「设计意图（fit 640×480 保比）」对表 8 张实卡几何**全部一致**

2. **`tb_scaler_real.v` 只判了图片「上边」黑边**
   - 首轮扫描 6 个分辨率里 4 个报 FAIL，而失败像素数**恰好等于黑边像素数**
     （1280×720→640×60=38400、640×200→640×140=89600、400×800→400×240=96000、1280×360→640×150=96000）
   - DUT 的 `iny=(dy>=offy)&&(dy<offy+dst_h)`、`inx` 同式，**四边都正确置黑**；是校验台漏判
   - 补 `in_rect` 四边判据后，640×200 / 1280×360 / 400×800 全部 **wrong px=0 PASS**

## 七、诚实的边界

- **花屏的确切微观机制涉及加密 IP `sdr_as_ram.enc.v`**，沙箱内无法直证。
  我能证明的是：**驱动它的那个「突发」被消除了**（wfifo 水位 511→50，写侧不再占口），
  且**溢出丢字（0x18）已被实测消灭**。是否完全消除屏幕花屏，**要看你的屏**。
- **板端串口读不到**：Anlogic 编程器在位（所以能烧），但 CH340/串口器件不在设备树，
  COM4 是残留项 → `WHY?/LIST?` 全「当前未连接」。所以我没法替你读板子状态。
- **残留时序观察**：intra-clock 保持裕量 `HWNS -0.054ns / 2 Viol Endpoints`
  （全局 HWNS -1.528ns 含跨时钟域异步路径）。历代基线报告只留了 WNS 汇总行，无法逐项对比；
  设计功能未变，判为既存项，记录待察。
- **1280×720 的复核还在跑**（该分辨率单跑约 25 分钟），结果会落
  `tools/tests/_b3/geom_sweep2.txt`。
