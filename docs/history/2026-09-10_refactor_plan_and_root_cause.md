## 1. 结论先行：花屏不在你修了六版的那一层

过去六个版本的全部努力（b17 看门狗 → b18 池开 → b19 三重锁 → b20 重试狗 → b21 半拍限流 → b22/22q 真四分频 → b23 读写让路）都集中在：

> **SDRAM 读写仲裁层**（`frame_fifo_read.v` / `frame_fifo_write.v`）

而真正的花屏发生在：

> **像素渲染层**（`img_scaler.v` 的缩放路径）

两者中间隔着一整个 SDRAM。这就是为什么每一版"代码级坐实"之后上板依然花 —— **诊断层次错了**。

### 1.1 为什么 b20 不花、b21 之后全花（此前误读为"限流引入回归"）

关键在 `img_scaler.v` L53：

```verilog
wire guard_c = c_ex0;                       // 仅当 src 恰为 640×480 才直通
wire        c_ex0  = (src_w == 16'd640) && (src_h == 16'd480);
```

- **b20 时代**卡上是 4 张标准 640×480 → `guard_c=1` → **走 `pass` 直通旁路**，整条缩放链路（除法、4 行环形缓冲、最近邻采样、letterbox）**根本没参与** → 画面干净。
- **现在**卡上是 `tools/multires_demo` 的 8 张多分辨率图组，实测 BMP 头：

| 图 | 实际尺寸 | 路径 |
|---|---|---|
| BMP0000 | 640×480 | 直通（唯一不该缩放的） |
| BMP0001 | 1280×720 | **缩放** |
| BMP0002 | 800×600 | **缩放** |
| BMP0003 | 400×800 | **缩放** |
| BMP0004 | 1024×768 | **缩放** |
| BMP0005 | 320×240 | **缩放** |
| BMP0006 | 640×200 | **缩放** |
| BMP0007 | 1280×360 | **缩放** |

**7/8 全进缩放路径。**团队把"TF 卡换成了多分辨率图组"这个变量当成常量，于是把一条新架构通路上的固有缺陷，误判成了 b21 引入的代码回归 —— 从那一刻起，后续六版全部修在了错误的层。

## 2. 花屏根因（量化坐实）

### 2.1 缺陷：4 行环形行缓冲，**写侧零背压**

```verilog
// L92    环形缓冲只有 4 行（slot 2bit）
reg [23:0] ring [0:8191];
// L196-205  S1 写侧：in_en 来一个写一个，既不检查 ring 深度，也不反压上游
if (actq && !pass && in_en) begin
    ring[wr_addr] <= in_data[31:8];
    ...
end
// L220  S2 读侧：b-22q 四分频，4 拍只开窗 1 拍
if ((row_ok || eovr) && (pass || (half_cnt[1] && half_cnt[0]))) begin
// L113  唯一的保护，只拦「读超前于写」
wire        row_ok = (rows_done > syc);
```

`row_ok` 保证的是 `rows_done - syc ≥ 1`，**完全没有保证 `rows_done - syc ≤ 4`（缓冲深度）**。

写侧速率由 SD 灌数据决定（每拍 1 像素），读侧被四分频限到 4 拍 1 字 —— **写比读快 4 倍，`lead` 单调增长，必然越过 4 行，正在读的源行还没读完就被后续源行覆写。**

### 2.2 量化结果（`python tools/opt_surgery/ring_probe.py`）

```
写侧 wdec=1 (每拍1像素,无背压)   读侧 decim=4 (四分频)   缓冲深度=4 行

BMP0005  320x240   -> OVERRUN 首次 @clk=1600   输出行 dy=0   已写至 5 行, 领先 5 行
BMP0002  800x600   -> OVERRUN 首次 @clk=4800   输出行 dy=1   已写至 6 行, 领先 5 行
BMP0004 1024x768   -> OVERRUN 首次 @clk=10240  输出行 dy=3   已写至 10 行, 领先 5 行
BMP0001 1280x720   -> OVERRUN 首次 @clk=17920  输出行 dy=6   已写至 14 行, 领先 5 行
BMP0003  400x800   -> OVERRUN 首次 @clk=2000   输出行 dy=0   已写至 5 行, 领先 5 行
BMP0006  640x200   -> OVERRUN 首次 @clk=3200   输出行 dy=1   已写至 5 行, 领先 5 行
```

**每张图在第 0~6 输出行就首次越界** —— 不是偶发抖动，是**每帧从第一行错到最后一行**。这与"整屏花"的现象完全吻合。

### 2.3 次生缺陷：`eovr` 在帧尾直接绕过 `row_ok`

```verilog
if (in_eov && actq) eovr <= 1'b1;          // L158
... && (row_ok || eovr) && ...             // L220：一置起就不再校验
```

`eovr` 只在下一帧 `in_sov` 时清零（L153）。帧尾出货期间连唯一的 `row_ok` 都失效。

### 2.4 一个反直觉但重要的推论

**b21 / b22q 的"限流"不是修复，是恶化因素。**限流把读侧再砍 4 倍，把读写速度差从 1:1 拉到 4:1，`lead` 增长更快、越界更早。所以"无限流的 b20 干净、加了限流就花"这条观察是对的，但归因错了：**不是限流引入了新 bug，而是限流放大了一个一直存在的缓冲设计缺陷。**

### 阶段二：修复 img_scaler

| 方案 | 做法 | 状态 |
|---|---|---|
| **A. 真握手背压** | 增 `in_ready`，仅当 `rows_done ≤ syc+3` 时收数 | ✅ **已落地并仿真 PASS**（commit `10dec84`） |
| **B. 弃用行缓冲，改 SDRAM 随机读** ★ | 源图已在 SDRAM，输出行需要哪几个源行直接随机读 | ⬜ 待做（**最终形态**） |
| C. 扩 ring 深度 | 4 行 → 8/16 行 | ❌ 治标，BRAM 已用 24/64，否决 |

A 方案落到 `user_source/hdl_source/img_scaler.v`，三处改动：

```verilog
+ output wire in_ready;                                  // 新增握手口
+ localparam [3:0] RING_DEPTH = 4'd4;
+ wire [16:0] lead_lim = {1'b0, syc} + (RING_DEPTH - 4'd1);
+ wire        room_ok  = ({1'b0, rows_done} <= lead_lim);
- if (actq && !pass && in_en) begin
+ if (actq && !pass && in_en && room_ok) begin
+ assign in_ready = pass ? 1'b1 : (actq && room_ok);
```

两个细节很关键：
1. **不能用 `row_ok` 兼作写侧门控** —— 它在帧首为 0，复用会直接死锁写侧（实测踩到）。
2. **用加法不用减法** —— `{rows_done - syc}` 无符号回绕会误判，加法形式无此风险。

#### 🔴 A 方案已证伪（11:10 决定性实验）—— 不仅仅是"没闭环"，是方向错误

上一节说"in_ready 悬空，TD 会优化掉"——**这个判断是对的，但后果比预想严重得多**。

为验证 A 到底有没有价值，新建了 **真实数据源模型 TB**（`tools/tests/tb_scaler_burst.v`），
把上游从"理想连续源"换成"SD 卡扇区突发源"，并加了上游脉冲计数器做账目核对。
结果彻底颠覆了原结论：

**实验矩阵（同一份 DUT 代码，只换上游源模型）**

| DUT | 上游源 | 突发长度 | 错误像素 | 判决 |
|---|---|---|---|---|
| 原始(未修) | 连续源(跟随DUT写指针) | — | **301324 / 307200 (98.09%)** | FAIL |
| 原始(未修) | 突发 push | 512 / 6512 | 0 (0.00%) | PASS |
| 原始(未修) | 突发 push | 1024 / 6512 | 0 (0.00%) | PASS |
| 原始(未修) | 突发 push | 2048 / 6512 | 0 (0.00%) | PASS |
| 原始(未修) | 突发 push | 4096 / 6512 | 277968 (90.48%) | FAIL |
| 原始(未修) | 突发 push | 8000 / 4500 | **304261 / 307200 (99.04%)** | FAIL |
| fix-A | 连续源 | — | 0 (0.00%) | PASS |
| fix-A | 突发 push | 8000 / 4500 | **305280 / 307200 (99.38%)** | **FAIL** |

**三个结论，每一个都推翻原计划：**

**① 旧 TB 的"连续源"是错的模型。** 它跟着 DUT 写指针走（DUT 停它就停），
这等价于"上游能感知反压"。真实 SD 卡是 push 型，`bmp_read` 状态机自主推进，
根本不理 DUT 死活。旧 TB 之所以能复现花屏，是因为连续源恰好把写侧推到最快——
也就是说**旧 TB 复现的是"上游不受控地快"，与板上的真实机制只是巧合同向**。

**② 花屏的真实触发条件是「上游连续推送长度」，不是"写快读慢"的均值。**
突发越短、间隙越长，写侧被拖得越慢，越不容易覆写。512/1024/2048 全部侥幸通过，
4096 起开始崩。精确判据（`tools/opt_surgery/ring_race_exact.py`）：

```
写侧推完 1 源行(800px)耗时   :  1560 拍   (含 gap 摊销)
读侧绕完 4 槽(4*640*4)所需   : 10240 拍
ring_turn 拍内写侧推进       :  6.56 行  >  RING_DEPTH = 4  ->  覆写 ✅解释实测
```

**③ A 方案在真实拓扑下不但无效，而且是有害的。**
`in_ready` 无人消费 → 门控挡下的是"DUT 拒绝写入"，而上游照样把像素推走。
账目核对（`dbg_burst.out`）：

```
fix-A : rows_done = 365 / 600 行   out_pixels = 186880 / 307200   ← 丢了 40% 数据
原始  : rows_done = 600 / 600 行   out_pixels = 307200 / 307200   ← 数据全收下
```

**fix-A 用"丢像素"换来了"不覆写"，而降速后环缓冲不再溢出，于是既不花屏也不花屏地缺块——
但帧永远送不满 307200 字，`frame_fifo_write` 的 `write_finish` 契约被打破 —— 这正是 b-19 注释里
警告过的那个坑。** 直接上板的表现会是：不花屏了，但画面缺 40% 内容 / 或者卡死在 `S_END` 前。

**根因因此修正为：img_scaler 的 push 型输入接口本身与上游不匹配。**
只要上游是 push 且无 ready 通路，任何"在下游做流控"的方案都只能是二选一：
要么覆写（原版），要么丢数据（fix-A）。**B 方案不是"更优选择"，是唯一解。**

**A 的唯一价值**：它证明了"写侧零背压"这一事实（fix-A 在理想源下确实 0 错误），
从而确定了根因所在的**层**；但它不能作为落地形态。
