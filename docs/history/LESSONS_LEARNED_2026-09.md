## ⚠️⚠️ 2026-09-12 12:45 重大定性：**「花屏」的真身是「卡的图源不合格 → 无图可播」**

**两个硬证据（缺一不可，务必先取这两个再谈别的）：**
1. **数码管显示 `img_found_count`（v12.3 起挂在数码管低两位，十六进制）** —— 实测 **`00`**
   → 卡扫描**一张图都没找到**。
2. **屏幕实拍**：**全黑**，只剩 OSD 横幅 `ANLOGI EG4S20 EMERGENCY INFO TERMINAL V2.1` /
   `SYSTEM READY - AWAITING`（右端被裁），左上角一小块绿色短条（帧缓冲残留）。
   → **视频层是空的，根本没有图在播**，不是「图在播但画错了」。

**真因**：`bmp_read.header_match` 只认 **24bit + BI_RGB 未压缩** 的 BMP
（`header_0/1=='B','M'`、`bit_count==24`、`compression==0`；`scale_en=1` 时另需
`mr_ok`：320≤w≤1280、16≤h≤1080、比≤4:1、w%4==0）。
用户卡上大概率是 **JPG/PNG**（或 32bit/带压缩 BMP）→ 一张都匹配不上。
官方 `HX4S20_Contest_202606/tools/bmp_check.py` 注释把同类坑全部点名
（含「**分辨率不匹配 → 显示错位或花屏**」）。

**修法（不用改 RTL，改卡内容）**：
- 校验 `bmp_check.py <卡目录>`；转换 `bmp_convert.py <图目录> -o <出目录> --size 640x480 --mode pad`
  （保证 24bit/未压缩/bottom-up/4B 行对齐，转完自动复验）
- **最快**：拷工程自带的 8 张演示图到卡根目录 `C:\td_batch\lab_pro\tools\multires_demo\BMP0000..0007.BMP`
  （已过官方校验 8/8；`scale_en=1` 下全在合法域 → 走缩放路，正好演示扩展 3）；拷完数码管应变 `08`。

**★★ 最重要的一条方法论（本文件最高优先级）**：
**先确认「信号源是否有效」，再谈「渲染是否正确」。**
2026-09-12 我花了整轮算力在 img_scaler / SDRAM 仲裁上找「花屏」，
真因却在**输入素材格式**。**一张屏幕照片（用户一句话的成本）就能立刻区分

## ⚠️ 花屏问题（2026-09-12 01:2x 重新定案，推翻 09-11 结论；优先级最高）

### v12.2 追加：`scale_en` 默认值 = 「只显示两张图片」的真因（已修）
- `msg_ink.v` 上电默认 `scale_en = 1'b0`（原注释：v10.3「缩放默认关」，为"零回归"）。
  **后果**：`multi_res=0` → `bmp_read.header_match` 只认「**恰 640×480**」→
  **多分辨率图在装载时就整组被拒**（demo 卡 8 张里只有 640×480 那张能播）。
- **更糟的次生效应**：每被拒一次 → 0.8s 装载超时 → 静默重试 ×2 → `load_abort` → 全量重扫
  （黑屏 ~1.6s）。按一次 NEXT 就轮一遍 → 屏幕反复黑/闪/残帧，**看起来就像"花屏"**。
  这也解释了 09-08 那些 `stall burst`/`LIST 振荡` 告警的现象学。
- **修法**：默认改 `scale_en <= 1'b1`（已落地，commit `e3c959f`）。
  安全性：640×480 仍走**未改动的 pass 直通**；超范围图仍被 `mr_ok` 拒；缩放链路已全分辨率验证。
- **★ 为什么必须改默认而不能叫用户敲 `SC 1`**：本机 **CH340/串口器件不在位**
  （`GetPortNames()` 有 COM4 但 `serial.Serial('COM4')` → FileNotFoundError），
  播控台发不出任何命令，**用户只能按板上物理键**。→ 凡"必须发命令才可用"的功能都等于不可用。

→ **7/7 多分辨率 + 640×480 直通 = 缩放/渲染链路在真板速率下 100% 正确。**

- **★ 先读这条：09-11/09-10 的「环形缓冲被写侧覆写」结论已证伪，勿再据此做 B3 重构。**
- **真根因（新）：缩放器输出「突发化」**。缩放路出货曾是 1字/4拍 → 一整行 640 字在 2560 拍内
  灌向 **512 深** wfifo → 写侧二选一：溢出丢字（= 0x18 卡死）或为排空长时间占住 SDRAM 写口、
  把**显示读口饿死**（= 板上花屏）。源侧平均只需 1 字/~280 拍，原节奏快 ~70 倍。
- **为什么 b20 干净、b22q/b23 都花**：b20 时卡上只有 640×480 → `guard_c=c_ex0` 走 **pass 直通**，
  缩放链路（含突发）根本不参与；换成多分辨率图组后 7/8 图进缩放路，突发暴露。
  b23 的 `O_wr_busy` 诚实口径只在「空 FIFO 泊车」时松手，**突发期间有料仍 busy** → 花屏照旧。
- **修复（已落地）**：`img_scaler.v` v12.1 缩放路出货 **1字/4拍 → 1字/32拍**
  （`half_cnt[1]&half_cnt[0]` → `rd_tick[4:0]==5'd31`）。比需求仍快 8 倍、**不拖慢装载**；
  瞬时灌入速率降到 1/8，wfifo 水位贴地，写侧不再成串占口。**pass 直通完全旁路，节奏零变化。**
- **★ 关键证据：真板 SD 速率比旧 TB 慢约 100 倍（这是推翻旧结论的地基）**
  - `spi_master.v`：每字节 = 16 半周期 ×(clk_div+2)，`SPI_HIGH_SPEED_DIV=0` → ~32~36 sys_clk/字节
    → SPI ≈25MHz → **~2.8MB/s → 1 像素(3B) ≈ 96~108 拍**。
  - 实测旁证：`sd_card_bmp.v` L973「正常加载 ~0.55s」/ 640×480(921KB) → **1 像素 ≈ 180 拍**。
  - 旧 TB（`tb_scaler_burst` 1像素/拍、`tb_v103_fw` 同）**比真板快 ~100 倍**。
- **环形缓冲在真速率下不可能覆写**：覆写需源快于 **3.2 拍/像素**
  （写侧要在读侧绕 4 槽的 10240 拍内推进 >4 行=3200px）；真板物理下限 96 拍/像素，**慢 30 倍**。
  仿真实证：`tools/tests/tb_scaler_real.v` 320×240@180拍/像素 → **wrong px = 0 PASS**。
- **几何与渲染链路在真速率下都正确**：`scaler_golden_cmp.py` 的 `golden_geom()` 原**分子分母错位**
  （`t_nd` 取 `(w*480)//w`，而 DUT 是 `est_w ? (h*640)//w : (w*480)//h`），
  **仅 4:3 时两式相等** → 800×600 能过，**1280×720 / 400×800 等一律误判**。已修正。
  修正后与「设计意图(fit 640×480 保比)」对表 8 张实卡几何**全部一致**（1280×720→640×360 off60；
  400×800→240×480 off200；640×200→640×200 off140；1280×360→640×180 off150）。
- **附带落地：`src_pause` 源侧限流（v12.0）**：`rows_done >= syc+2` 时经
  `bmp_read.pause`→`sd_card_bmp.pause`→顶层，在**扇区间隙**暂停下一扇区读。
  安全不变式 `rows_done <= syc+3`。真速率下是 no-op（源本来就是瓶颈），仅作兜底。
  `sd_card_sec_read_write` 的 `S_WAIT_READ_WRITE` 天然等待 → **扇区间暂停无超时/协议风险**。
- **教训 1**：b17→b23 六版全打在 SDRAM 读写仲裁层，与真因（缩放器输出节奏）隔了一层。
- **教训 2**：**TB 的源模型必须与真板同量级**。旧 TB 快 100 倍 → 复现出一个真板不存在的
  「覆写」病，并据此设计了整套 B3 架构（属重大误导，已止损）。
- **教训 3**：`stall / LIST / walkall distinct` 全是 **SD 加载层**指标，对像素渲染层完全失明。
- **教训 4**：**`B=R+G` 这类「像素内自洽性」不能判覆写**——R/G 同行同字，整行被替换仍自洽。
  判覆写必须看**行号轨迹**（G 反推实际源行 vs 应有源行）。
- **教训 5**：**几何类的 golden 模型必须用「设计意图」独立对表**，不能只与 DUT 内部寄存器同式复算，
  否则「同错抵消」。本次 8 分辨率对表法已固化（见 `scaler_golden_cmp.py` 修正注释）。
